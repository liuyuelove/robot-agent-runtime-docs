    分层与边界 02

    分层的价值不在于"分了九层"，而在于每一层都能被一句话说清"不许做什么"，并且这句话是可以用测试检查的。

    九层职责

    层唯一职责明确禁止
    app应用与交互生命周期、composition root、确定性协调承载业务规则、写 graph node
    agentLangGraph、state、node、route、模型调用编排直接拿 live Adapter、持久化写入、操作设备
    domain纯业务模型、规则、guard、状态转移依赖 app/agent/tools/adapters/SDK/文件系统/环境变量
    tools模型可调用能力的合同与实现创建/管理 Adapter、读 YAML 或环境变量
    adapters设备、外部服务、进程内 Engine 的稳定边界被业务层反向依赖；Hardware/Integration 互相调用
    config读取、合并、冻结配置树集中 import 各模块 parser；运行期重载
    prompts提示词与工具使用策略读 YAML、拿 live Tool/Adapter、访问业务存储
    observability日志、指标、追踪定义业务状态、通过事件总线发命令
    shared确有跨层价值的基础类型变成绕过依赖规则的杂物间

    箭头只朝下。domain 在最底层且不依赖任何东西——它是唯一可以被单独拿去跑测试的层，也是唯一能在不碰任何 IO 的前提下验证业务正确性的地方。

    四条硬规则

    1 · graph node 不许碰 live Adapter

    node 只做"读 state、决定下一步"。它一旦能拿 Adapter，就会开始写设备、写数据库，然后这个 node 再也测不了。需要动作 → 交给 Tool；需要确定性协调 → 交给 app。

    2 · Tool 不许构造器注入 Adapter

    构造器注入看起来最"干净"，但它把"谁在什么时候拥有实例"这件事泄漏给了每个调用方。改成执行时向 facade 取，好处是：Adapter 未就绪时 Tool 能返回一个明确的"依赖不可用"错误，而不是在 import 期崩掉或者拿到一个半初始化对象。

    3 · Hardware/Integration Adapter 不许调用别的 Adapter

    否则依赖图会长成一张网，启动顺序无法确定，Mock 也无法隔离。要组合多个外部能力，那是 Engine 或 app 的职责，不是 Adapter 的。

    4 · 配置在启动期一次成型，运行期不可变

    没有热更新。看起来是倒退，实际上消掉了一整类竞态：不存在"配置读到一半被改了"的状态，也不存在"某个模块用旧值、某个模块用新值"的窗口。

    为什么这么较真

    因为这个系统的失效模式很讨厌：它不会崩，它会变得奇怪。机器人突然不迎宾了、说了两遍"已为您取号"、该回充的时候在闲聊。这类问题没有栈可以看，只能靠"每条事实都有唯一来源、每个状态转移都有唯一入口"来防。

    分层不是审美，是为了让"奇怪"有地方可查。
