    配置体系 11

    配置的目标只有一个：让"启动成功"这件事有意义。要么全部合法，要么根本起不来，不存在"起来了但某个模块拿的是默认值"。

    三级合并

    config.yaml        可提交的共享默认值
  < config.env     本机差异与敏感覆写（禁止提交）
  < 进程环境变量    最高优先级

    环境变量用双下划线表达层级，大小写不敏感：

    APP__MODEL__BASE_URL=http://192.0.2.10:7001/v1
APP__AGENT__DISPLAY_NAME=Local Agent

    环境变量只能覆写数据值，不能注入类路径或工厂函数。否则配置就变成了远程代码执行入口。

    启动期类型化

    读取 + 合并
    三个来源合成一棵原始配置树
    确定启用集合
    哪些模块 / 工具 / Adapter 实际启用
    逐模块构造类型化 Config
    只构造已启用的；任一校验失败 → 阻止启动
    冻结
    不可变对象，注入到最小必要范围

    通用配置层不认识任何具体模块的字段。它只负责读取、合并、冻结原始树和报告结构错误；具体字段的解析器属于各自模块，由 composition root 按启用集合去调用。这样加一个模块不需要改通用层。

    禁用模块不构造

    一个模块没启用，它的配置可以完全不合法——不校验、不构造、不 import 实现。这条规则省掉了大量"为了通过启动校验而写的假配置"，也避免了"配置看着有、其实没生效"的错觉。

    同时明确：禁用模块不许运行期懒加载。想用就重启，不支持"用的时候再打开"。

    不可变的代价

    不支持热更新，改配置必须重启。在云服务里这几乎是不可接受的，在机器人上是合理的：

    • 重启代价是几秒，而"配置改了但只有一半模块生效"的排查代价是几小时；
    • 运行期不可变消掉了一整类竞态（不存在读到半新半旧配置的窗口）；
    • 现场运维本来就很少改配置，改的时候有人在旁边。

    这是用部署形态换来的简化，不是通用最佳实践。换个场景结论可能反过来。

    字段所有权

    配置拥有不拥有
    Tool Config行为参数（阈值、超时、模板 ID）凭证、endpoint、provider
    Adapter Config凭证、endpoint、连接超时、重试、Real/Mock 选择业务规则
    模块 Config该模块自身开关与参数其他模块字段

    同一字段只能有一个所有者。这条规则挡住的最常见错误是：同一个超时值在 Tool 和 Adapter 里各配一份，然后某天只改了一处。
