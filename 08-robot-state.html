    机器人状态机 08

    15 个状态、两张矩阵、8 个 reaction 模块。这是整个系统里唯一一个"能做什么"和"能听见什么"都由配置文件决定的地方。

    15 个状态

    命名规则是 <场景>_<MOVING|STATIONARY>。用 STATIONARY 而不是 STANDING，因为语义是"停止移动"，不是"站着"。

    组含义两个子状态
    RESETTING_*回位（导航复位 / 巡检复位）回位途中 / 到位
    WELCOMING_*固定迎宾点驶向迎宾点 / 驻留开窗
    IDLING_*待机移动中 / 驻停
    BUSINESS_*业务办理带路中 / 停在业务点
    PATROLLING_*巡检巡检移动 / 巡检驻留
    GREETING_*移动迎宾（巡游）巡游中 / 停驻
    CHARGING_*回充前往充电桩 / 已驻桩
    EMERGENCY_STOPPED急停（无 MOVING 变体）

    启动状态固定为配置里的 initial_state（默认 IDLING_STATIONARY），然后由一次启动对账修正到实际物理状态（见本章末尾）。

    矩阵一：状态转移（15 × 15）

    行是当前状态，列是目标状态，1 表示允许、0 表示拒绝。对角线是 1——允许"切到自己"，用来吃掉重复请求。

    当前 ↓ / 目标 →IDLING_SBUSINESS_SCHARGING_SEMERGENCY
    RESETTING_MOVING✓✓✓✓
    IDLING_STATIONARY✓✓✓✓
    BUSINESS_STATIONARY✓✓✓✓
    CHARGING_STATIONARY✓·✓✓
    EMERGENCY_STOPPED✓··✓

    （片段示意，完整矩阵在配置文件里，共 15 行 × 15 列）

    几条被写进注释的硬规则，每一条都对应一次线上问题：

    规则为什么
    MOVING 不能直接到 MOVING否则会出现"一边走一边改目的地"，底盘指令互相覆盖
    所有闲置态都能进充电低电量必须随时能走
    急停可以从任意状态进入，但只能自环或解除到 IDLING_STATIONARY安全态不允许"恢复到急停前"——那个状态可能已经不安全了
    RESETTING_MOVING 必须能回到所有能进入它的驻停态导航失败补偿；否则会卡在回位途中出不来
    CHARGING_MOVING 不能直达 IDLING_STATIONARY必须经过到桩确认，避免"没插上电就走了"
    电源事实硬迁可为任意状态开 → CHARGING_STATIONARY物理插电就是事实，不需要经过导航

    矩阵二：事件转发（15 × 18）

    这张矩阵决定某个状态下，哪些事实能被"听见"。18 个源事件分四类：Brain Input（4）、Brain Output（8）、运动感知（6：环形麦方位、人体存在/离开、人脸候选、HumanExist/NoExist）。

    转发的产物固定命名为 RobotStateAware + 原类名，不在配置里重复声明。

    状态 ↓BrainInputReceivedLLM 流式分片环形麦方位人体在场HumanExist

    CHARGING_STATIONARY✓✓···
    EMERGENCY_STOPPED✓✓···
    PATROLLING_MOVING·✓✓✓·
    GREETING_MOVING·✓✓✓✓

    （片段示意，按类别各取一个代表列；完整矩阵 15 行 × 18 列）

    四条贯穿规则：

    • MOVING 状态基本屏蔽 Brain Input——机器人在走路时不该"听见"用户说话，否则会把路过的一句话当成需求；但 Brain Output 全部转发，因为正在播报的内容需要被追踪。
    • 例外不是笔误，是按用途开的：七个 MOVING 态里，回位 / 空闲 / 业务 / 充电四个全屏蔽输入；WELCOMING_MOVING 放行 Received、Partial 与人脸，只屏蔽硬件输入；PATROLLING_MOVING 与 GREETING_MOVING 放行人脸输入——移动迎宾和巡检要在走动中判断"前方有没有人"，屏蔽了就没法停驻。
    • STATIONARY 默认全放行 Brain I/O，只屏蔽运动相关事实（人已经在面前站定，不需要再靠"有人经过"来判断）。
    • 运动事实只在对它有意义的状态放行：环形麦方位只在 4 个状态转发（迎宾驻留、回位途中、巡检移动、移动迎宾），人体在场只在 3 个状态转发。
    💡

    这张矩阵的真正价值

    它把"机器人在什么状态下应该听见什么"从一个散落在十几个 if 里的隐式约定，变成了一张能评审、能测试、能一眼看出矛盾的表格。新增一个状态时，你必须同时回答 15 个"能不能转过去"和 18 个"要不要转发"。

    状态能干什么：能力准入

    转移矩阵只回答"能不能过去"，不回答"在这个状态能不能执行某个动作"。动作有各自的准入，通常是矩阵边 + 来源白名单双重判定。

    能力准入拒绝时
    navigate / rotate / translate矩阵允许 + 非急停emergency_stopped，不创建 operation、不下发底盘
    start_patrol / pause_patrol矩阵允许状态冲突码
    start_recharge（普通回充）矩阵边 + 白名单 {IDLING_STATIONARY, WELCOMING_STATIONARY}charge_state_not_allowed
    force_recharge（临界电量）白名单 {IDLING_S, WELCOMING_S, BUSINESS_S, PATROLLING_S}，任意驻停无条件出发整单拒绝，不污染在途 operation
    leave_charging（被动离开充电）仅 CHARGING_STATIONARY状态冲突，不改变状态

    为什么普通回充要拒绝 BUSINESS_STATIONARY 和 PATROLLING_STATIONARY：矩阵边已经为"强制回充"开放了这两行，如果不加白名单，普通回充会顺着这条边泄漏进去——客户正在办业务，机器人却因为电量策略走开了。这条叫"防泄漏"，是评审时专门加的。

    什么导致转移

    触发事实目标说明
    导航完成RESETTING_STATIONARY / CHARGING_STATIONARY / GREETING_STATIONARY按 operation 上下文判定是哪种目的地
    导航失败（起步前）回到来源态，或兜底 IDLING_STATIONARY来源不可回退时兜底，避免卡死在 RESETTING_MOVING
    导航失败（起步后）IDLING_STATIONARY不伪造"回到原地点"，不建新会话
    迎宾自然完成 / 人工停止GREETING_STATIONARY → RESETTING_MOVING先停驻，再调远端复位，等复位完成后才进 RESETTING_STATIONARY
    巡检停止 / 完成回迎宾点巡检有独立复位协议，不复用普通导航 reset
    电源事实 charging|fullCHARGING_STATIONARY硬迁，除急停外任意状态（含 MOVING）
    急停 TrueEMERGENCY_STOPPED任意状态，且优先于充电事实
    急停 FalseIDLING_STATIONARY仅当当前是急停态；不恢复急停前的状态
    会话不活跃超时RESETTING_MOVING由看门狗发起，带 expected_source_state 防误伤
    空闲关键词命中RESETTING_MOVING仅 IDLING_STATIONARY 下生效

    转移之后做什么：reaction

    状态转移只负责"落账"。落账之后要做的事分成两类，执行时机完全不同：

    类型例子执行时机
    提交后必执行创建会话迁移落账后同步执行
    仅当前 revision 有效发起导航、开启迎宾、巡检动作进入单线程队列，执行前校验 revision

    这个区分很关键：会话创建是"已经决定了必须做"的事，晚一步就会丢；而"发起导航"可能在排队期间状态又变了，所以执行前必须确认自己还是最新的那一次。

    reaction 按领域拆成 8 个模块：face / face_state / idling_reset / navigation / patrol / charging / greet / digital_human。它们只响应事件，不各自做第二套状态转移——状态只有 _commit_transition() 一个出口。

    顺带同步数字人

    每次真实迁移都会同步一次数字人运动状态，映射规则是纯命名约定：

    状态数字人 status
    所有 *_MOVING0
    所有 *_STATIONARY2
    CHARGING_STATIONARY（且禁止聊天显示时）6

    不做去重，每次迁移直接转发。因为数字人侧是有状态的，去重反而会让它和真实状态漂移。

    三个迁移日志

    事件时机级别
    robot_state.transition.changed真实变化INFO
    robot_state.transition.rejected矩阵拒绝WARNING
    robot_state.transition.idempotent接受但状态未变DEBUG

    三者共用一个出口，字段统一带 source_state / target_state / requested_by / revision / error_code。日志写失败不影响迁移结果。

    回充：最复杂的一条链路

    回充是状态机里唯一有"两个入口 + 局部幂等 + 上下文对账"的链路，值得单独说。

    两个入口，共用一条提交路径

    start_recharge()   普通回充（定时 / 低电量）
force_recharge()   临界电量强制回充
        \          /
         _submit_charge()
              |
    状态准入（各自白名单）
              |
    （仅 force 且来源为巡检驻留时：轻量停巡，不 reset 回起点）
              |
    通过 Public Navigation 提交导航到充电桩
              |
    登记 operation，由导航终态收口

    局部幂等：复用而不是新建

    如果同一个目的地已经有一个自己创建的 operation 在跑（已 Accepted/Started、未收终态），再来一次 start_recharge()：

    • 复用原 operation_id，不创建第二个导航；
    • Receipt 返回 accepted=True 但 changed=False；
    • 原 operation 的终态仍按原上下文收口。

    如果导航里存在一个不是自己创建的同目标 operation，则不接管、不登记，直接返回 navigation_busy。这条幂等只属于回充控制器自己拥有的 operation，不是系统级保证。

    上下文对账：revision 重钉

    处理导航事件前，先检查自己持有的上下文是否还有效：

    情况动作
    当前状态名 ≠ 上下文期望状态名作废上下文，不处理本事件，不推进状态
    状态名相同但 revision 变了只重钉 revision，继续处理

    关键在于不因为"revision 不同"就作废——revision 会因为无关的迁移而增加，一看到不同就丢上下文会导致回充永远收不了尾。

    两条离开路径

    路径入口目标语义
    主动退出reset()RESETTING_MOVING要回迎宾点
    被动离开leave_charging()IDLING_STATIONARY充电对账确认失败，不走了，就地待机

    两条路径的 requested_by 不许混用。被动离开不调导航、不发底盘停止命令、不建会话——它只是"承认这次充电没成"。

    电源事实硬迁

    物理插电时，底盘会报 charging|full。这条事实会让状态机从任意状态（除急停）直接跳到 CHARGING_STATIONARY，包括 MOVING。

    迁完会清理所有运动残留（导航、回充、巡检、迎宾、环形麦的上下文），但不调导航取消、不发底盘停止——因为物理插电本身就意味着已经静止了。

    反向（discharging）不迁移。拔电退出统一交给 app 层的断充确认窗口处理。原因是：如果在状态机里立刻硬释放，那个 20 秒的确认窗口会在 1 毫秒内空转。

    急停与启动对账

    安全态优先

    任意状态 -- 急停 True --> EMERGENCY_STOPPED
EMERGENCY_STOPPED -- 充电事实 charging/full --> 忽略（不覆盖）
EMERGENCY_STOPPED -- 急停 False --> IDLING_STATIONARY

    急停由导航适配器发布，状态机自己不推断急停（普通导航失败不等于急停）。急停态允许聊天，但禁止一切运动能力。

    解除只能由解除事件驱动。手动 API 可以切入急停，但不能从急停态手动解除——安全态不允许被软件按钮放开。

    启动对账

    进程启动时状态固定是配置的初始值，但机器人可能正插着电、或者急停按钮被按下。所以全部 Adapter 启动完成后会延迟（默认 5 秒）做一次level 对账：

    优先级：急停 > 充电 > 默认

导航快照 emergency_stop 为真（或读取失败）→ EMERGENCY_STOPPED
充电快照 connected 且非 stale 且 power_state ∈ {charging, full} → CHARGING_STATIONARY
否则 → 保持启动默认态

    为什么要延迟 5 秒：需要等导航和充电客户端连上并交付第一条事实。数据 stale / 未知 / 未装配时一律 fail-closed，不迁充电。

    对账是幂等的——已经在目标态就不迁移、不 bump revision。运行期之后的变化仍由事件驱动，不重复收敛。
