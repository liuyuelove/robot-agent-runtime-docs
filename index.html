    服务机器人
    Agent 运行时

    一台运行在线下服务场景里的机器人：轮式底盘、业务屏、数字人、环形麦阵。 一个 LLM Agent 站在中间，决定"现在该说什么、该调哪个能力、该把机器带到哪"。 这里记录的是它的骨架，以及为了撑住这套骨架做出的取舍。

    关于这份笔记

    这是个人技术总结，不是任何公司的产品文档。所有源码、配置、内网地址、设备型号、业务话术与客户数据均已剔除或抽象为占位符。 文中出现的 <llm-gateway>、192.0.2.10（RFC 5737 文档保留地址）、某厂商底盘 等，全部是占位符，不代表真实取值。

    这是什么

    一套部署在单台边缘机器上的具身智能体运行时。它要同时应付三类输入：

    • 人——走近、被唤醒、说话、被记住长相；
    • 设备——底盘位置、电量、业务屏状态、取号结果、充电桩握手；
    • 模型——一个会调工具、会跑偏、会说错话的 LLM。

    然后把它们收敛成一条可预期的主线：迎宾 → 对话 → 办业务 → 送别 → 回位 / 巡检 / 回充。

    真正难的地方不在"接一个大模型"，而在于：27 个外部设备与服务、18 个可被模型调用的能力、15 个机器人状态、十余条互相竞争的计时器，要在一个没有运维介入的单机进程里长期稳定地跑。

    三个绕不开的工程难题

    难题具体表现采用的解法
    长尾设备接入 底盘、业务屏、自助设备、环形麦、数字人、充电桩、门禁……每个厂商一套协议；换一个型号就要改一片代码 Adapter 三分类 + Real/Mock 合同一致 + 统一生命周期；上层只认语义方法，不认协议
    模型行为不确定 同一个问题两次调用工具不同；该说"好的"的时候开始编业务规则；设备还在动就宣布"已到达" Tool 合同约束输出；状态机约束动作；设备事实事件约束"已发生"的判定权
    多人 + AI 协作 12 个人、897 次提交、大量 AI 生成代码；风格、边界、命名三天就漂移 单一准则目录 + 模块双文档（README/AGENTS）+ 21 个架构守护测试把规则变成 CI

    技术栈

    层选型说明
    语言Python 3.11+类型注解 + Pydantic v2
    AgentLangGraph / LangChain单 agent + 工具调用，不用多 agent 编排
    服务FastAPI + UvicornHTTP + SSE + WebSocket，进程内多路并发
    配置YAML + env三级合并，启动期构造为不可变类型化对象
    观测自研 JSONL schema单行结构化日志 + 按 Run 聚合的耗时分析脚本
    测试pytest / pytest-asyncio默认用例不依赖真实 LLM、网络或硬件
    部署单机进程边缘侧，无容器、无外网依赖；这也是很多设计的约束来源

    系统全景
    一次完整交互要经过哪几个边界，谁持有谁，进程里到底跑着什么。
    ⏱️
    端到端时序
    从声波到播报的九跳，T0–T12 时间轴，三条打断路径与延迟锚点。
    🏗️
    分层与边界
    九层职责、依赖方向，以及"为什么系统里不允许出现 Dispatcher"。
    🔌
    Adapter 体系
    三类判定、Real/Mock 合同一致、Runtime 生命周期与 facade 唯一入口。
    🧰
    Tool 体系
    代码注册作为唯一事实源，Schema 与入口自动推导，YAML 只管开关。
    📡
    事件驱动
    事实总线与命令总线的分野，以及为什么它不承诺顺序和幂等。
    👤
    会话生命周期
    单活跃会话模型、人脸驱动的会话切换，以及三类倒计时与六个暂停源。
    🤖
    机器人状态机
    15 个状态、两张矩阵：什么能转过去，什么状态下能听见什么。
    🗜️
    上下文压缩
    预算模型、CAS 提交，以及"办过"和"办成了"为什么必须分开存。
    📝
    提示词工程
    prompt 是代码：按启用的工具拼装，模型看不到一个没启用的工具。
    ⚙️
    配置体系
    三级合并、启动时一次性构造类型化 Config，运行期不可变。
    🔍
    可观测性
    结构化日志、事件流与快照，出问题时从哪一层开始查。
    🧪
    测试策略
    21 个架构守护测试：把"不许这么写"变成会红的 CI。
    🤝
    AI 协作开发
