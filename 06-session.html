    会话生命周期 06

    系统里任何时刻只有一个活跃会话。真正的难点不是"怎么创建会话"，而是"什么时候该换掉它"——一半由人脸的来去决定，另一半由一张六源暂停矩阵决定。

    单活跃会话

    ActiveSessionManager 是进程内唯一权威：它持有当前 session_id、一组 SSE 订阅队列和激活回调。所有输入都必须带 session_id，不匹配直接拒绝（inactive_session），不会"猜一个最近的会话"。

    🎯

    为什么不做多会话

    因为物理前提不成立：一台机器人面前站着一个人。多会话会立刻带来"这段语音属于谁"的归属问题，而答案只能靠猜。

    会话从哪来

    来源触发说明
    迎宾开窗进入 RESETTING_STATIONARY / PATROLLING_STATIONARY / CHARGING_STATIONARY状态机在迁移落账后、reaction 入队前调用一次 session creator
    人脸锁定稳定人脸出现最常用的一条；见下节
    管理平台召唤POST /v1/web-summon导航到达后才激活新会话，到达话术不写进召唤前的历史
    回充到桩CHARGING_STATIONARY 进入保留"到桩建会话"语义，便于充电时也能对话

    有一条细节：来自不活跃看门狗的复位链会把 skip_session_creation 置为 True，避免"超时重置 → 回位 → 再建一个会话"这种连环副作用。

    什么时候换会话：人脸驱动的切换

    这是会话层最复杂的一段，参数全在配置里：

    阶段判定默认值
    稳定锁定同一 face_id 在时间窗内出现足够多帧10 帧 / 1.0 s
    离开去抖连续丢失足够帧才认为离开10 帧 / 1.0 s
    离开确认去抖通过后再等一段确认时间3.0 s
    继任人脸送别完成且新面孔稳定独立的一套确认计数
    档案重注入对话进行 N 轮后重新注入档案5 轮

    为什么要"去抖 + 确认"两段：人转头、低头看手机、被路过的人挡住，都会造成短暂丢帧。只看"这一帧有没有脸"会让会话疯狂地开关。三段判定（帧数 / 时间窗 / 确认期）分别挡住瞬时噪声、抖动和"真的走了"。

    送别与继任

    送别完成、且新面孔稳定之后，编排器会记录一条 face_changed 事实，直接携带前后两个 face_id、前后两个 session_id、是否重置会话以及原因。

    这条日志是刻意设计的：它只陈述"已经完成的 app 协调事实"，不新增公共 Event。原因是——这件事已经发生了，不需要再广播一次让别的模块去反应；但排查"为什么这个客户的话接不上"时，又必须能一眼看到换人发生在哪一刻。

    什么时候自动结束：不活跃看门狗

    换会话有两种方式：人脸驱动的切换，和时间驱动的重置。后者看起来简单——"20 秒没人说话就重置"——实际上它是这一章里最长的一段代码，因为它要回答"这 20 秒到底该不该算"。

    三类倒计时，不是一种

    类型何时装载默认时长
    idle驻停待机、无对话20 s
    moving_welcome移动迎宾过程中5 s（按入口来源再细分）
    charging进入充电态时不启动，只有收到聊天输入才启动一轮20 s

    另外还有两条独立的时间线，不参与上面的超时重置：

    • 定时移动迎宾：只在配置的星期与时间窗内（默认 08:00–17:00）启动 600 s 倒计时，到点才出发巡游；
    • 唤醒回正：被唤醒并转向声源后，等待旋转完成，再起 15 s 倒计时回正。
    ⚠️

    充电态为什么不启动倒计时

    充电时机器人本来就不该"因为没人说话而离开"。只有客户真的开口聊了，才进入可对话状态并开始计时；超时后回到充电态，但不改变机器人状态（不触发回位）。

    六个暂停源

    倒计时不是简单的"重置计时器"，而是：任一个暂停源有效就取消计时，全部释放才重新装载一个完整倒计时（不是续期）。

    暂停源触发事实解除兜底
    业务屏占用
    作用于全部倒计时    		 页面已打开 / 交易已开始 页面退出 / 交易完成 / 异常结束 / 步骤超时 / 业务超时 600 s（仅无关联点击）
    导航进行中
    作用于全部    		 导航 Accepted 导航终态（完成 / 失败 / 取消） 导航自身超时
    语音播报中
    作用于全部    		 TTS Started Finished / Interrupted / Failed（需 request_id 匹配） 60 s 静默
    人脸在场
    仅 idle、charging    		 稳定人脸锁定 离开确认 —
    人体在场
    仅 idle、charging    		 近场检测到人 离开去抖 —
    机器人状态门禁
    按状态    		 状态不允许计时（如 MOVING） 状态回到驻停 —

    矩阵的两条语义

    1 · 暂停是"取消"，不是"暂停"

    代码里没有 timer.pause()。暂停 = 把当前 timer 取消掉；恢复 = 用完整时长新建一个。这样不存在"剩余时间"这个概念，也就不存在"暂停太久导致剩余时间算错"。

    2 · 人体事件是持续事实，不是边沿

    这一条踩过坑。人体检测上报的是"现在有人/没人"，不是"刚刚来了"。如果每收到一次 present 就刷新倒计时，只要人站在那不动、传感器持续上报，倒计时就永远不会到期。

    处理方式是：

    if 已处于暂停状态:
    取消计时（保持暂停）
elif 确认已无人:
    重新装载完整倒计时
else:
    什么都不做（腿在、脸不在，不续期）

    配合一个开关 pause_when_human_present_requires_face_present：只有"人 + 脸"同时成立才算有效在场。否则人从机器人背后走过也会一直卡住会话。

    最难的一格：无关联的屏幕点击

    客户直接上手点屏幕时，设备只上报"某通道进入处理中"，没有 operation_id 能和当前会话对上。这条路径必须特殊处理：

    1. 把该通道临时绑定到当时的活跃会话，暂停倒计时；
    2. 通道离开处理中（正常终态）→ 解除临时暂停；
    3. 如果设备再也没报终态（拔网线、断电）→ 600 s 保险丝强制解除；
    4. 解除后不因为快照里还残留"处理中"就立刻重新暂停——否则会陷入"解除 → 立刻暂停"的死循环，必须等到下一次明确的开始事实。

    这一格在评审时被推翻过两次，最后单独写了一份事件矩阵设计文档，因为它的正确性无法靠读代码看出来，只能靠穷举。

    定时移动迎宾

    迎宾点驻留时，如果当前在配置的时间窗内，启动一个长倒计时（默认 600 s）；到点就出发巡游一圈，回到迎宾点再开窗。

    规则行为
    总开关关闭完全不启动
    当前星期不在列表不启动
    当前时间不在任一区间不启动；已在计时则取消
    倒计时到期时已离开时段跳过本次巡游，不补跑
    跨午夜区间仍按当前本地日期的星期匹配，不把已选星期延续到次日凌晨

    最后一条是刻意的：如果按"区间起始日"算星期，那么周五 23:00 启动的跨午夜区间会一直有效到周六凌晨，而周六可能本来不在排班表里。

    为什么值得写 1800 行

    因为这段逻辑的失效方式是静默的：计时器早关了一秒，用户话说到一半被重置；晚关一秒，机器人对着空椅子继续说欢迎语。没有异常、没有栈，只有"今天感觉有点怪"。

    而它依赖的事实源有六个（状态机、导航、语音、人脸、人体、业务屏），任何一个的上报节奏变化都会影响结果。把它写成一个显式的矩阵，是唯一能评审、能测试、能在改动后确认没退化的方式。

    会话里存什么

    一个会话有两份历史，用途完全不同，不能混用：

    session.messagesfrontend timeline
    用途模型上下文前端渲染
    内容含 assistant.tool_calls、tool 等协议记录只有用户消息、助手消息、工具调用、状态操作
    维护者Runtime / SessionRepositoryConversationEventProjector

    页面刷新恢复不读 session.messages——那是给模型看的，里面混着协议字段，直接渲染会露出 tool_call_id 这种东西。前端只信 timeline。

    输入先落库

    正式输入在 admission 阶段就先写一次库（role="user"，带 input_id:user 作为 message_id），然后才执行 graph。这样即使这一轮马上被新输入抢占取消，用户说过的话也不会丢。

    每轮都有明确终态：succeeded / failed / cancelled。被取消的回合丢弃缓冲的助手文本，但输入消息以 completion_kind=no_reply 闭合——否则这段历史永远"没结束"，会永久阻塞后续压缩。

    一次会话的完整时序

    人脸稳定锁定
    10 帧 / 1.0 s → 预取 face_profile
    创建并激活会话
    旧会话保留历史，新会话成为唯一活跃会话
    注入档案与开场
    档案作为 SessionPatch 合入；固定开场话术走模板输出
    多轮对话
    输入先落库 → graph → 流式输出 → 终态闭合
    送别
    离开去抖 + 3 s 确认 → 固定送别话术
    收尾与继任
    会话记忆摘要 → 若已有继任人脸则直接切换，否则回待机

    注意最后一步：会话结束和"下一个人开始"是两件事。中间可能隔很久，也可能只隔一秒（两个人交替）。继任人脸的独立确认计数就是为了处理后者。
