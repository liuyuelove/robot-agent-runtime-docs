    提示词工程 09

    这套系统里的 prompt 不是一段写在配置文件里的文本，而是一组能 diff、能测试、能按开关拼装的代码。它最重要的性质是：模型看不到一个没启用的工具。

    prompt 是代码，不是配置

    它放在 src/prompts/ 里，和业务代码同一个仓、同一条流水线。配置里只出现版本号，永远不出现文本：

    agent:
  prompt_version: v2_0818   # 只有名字，没有内容

    这个选择的直接后果是：改 prompt 是一次代码提交，会进 diff、要过 review、能跑测试。反过来，如果 prompt 存在 YAML 里，改一个字不会有任何测试变红——它悄悄改变系统行为，而没人能证明它变了。

    💡

    为什么不用模板引擎

    模板引擎擅长"填空"，但 prompt 的主要变化不是填空，而是整段出现或消失——某个工具没启用，它那一整节说明就不该存在。用 Python 函数返回字符串，判断逻辑和文本放在一起，比在模板里写一堆 {% if %} 更直白。

    一个版本长什么样

    不是一个大字符串。每个版本是一个包，由几个模块拼成，每个模块是一个返回字符串的函数：

    模块行数内容
    identity.py5身份与不可越界的硬约束（不索取敏感信息、回复长度上限）
    behavior.py7普通对话下的行为边界
    tool_usage.py93业务工具集的用法与决策顺序
    non_business_tool_usage.py169非业务工具（导航、检索等）的用法

    拆开的好处很具体：改一条业务规则只动 tool_usage.py，身份设定和通用行为不在同一个 diff 里。审的人一眼能看出这次改的是"身份"还是"流程"。

    顺带说一个数字对比：最小的一版 158 行，最大的一版 536 行。同一个位置的 prompt，体积差了三倍多——这说明它不是"一次写好"的东西。

    核心：工具说明跟着工具走

    这是整套设计里最关键的一条。工具说明不是写死在 prompt 里的，而是按实际启用的工具拼出来的。

    # prompts/tools/weather.py
REQUIRED = frozenset({"search_weather", "format_forecast"})

def weather_section(enabled_tool_names: frozenset[str]) -> str:
    if not REQUIRED <= enabled_tool_names:   # ← 不满足，整段不渲染
        return ""
    return """## 查天气
- 客户问天气时调用 search_weather，city 必须来自客户原话。
- 预报结果用 format_forecast 排版，不要自己编造温度。"""

    这段代码的价值不在写法，在它的失败方式：只要工具没启用，这一节就不存在，模型不可能看到它、也不可能去调它。

    对比手写 prompt 的常见事故：删掉了一个工具，忘了删对应的说明。模型读到了说明，去调一个不存在的工具，报错、重试、绕圈。这类问题在拼装结构里在语法层面就不可能发生——不是靠人记得，是靠代码结构。

    💡

    可迁移的一条

    凡是"两处必须保持一致"的地方，别靠纪律，改成让第二处由第一处生成。prompt 和工具集的关系就是典型：不是"记得同步"，而是"根本没法不同步"。

    七个版本怎么共存

    注册表是一个字典：版本名 → 构造函数。不认识的名字直接抛错，并把支持列表打出来——快速失败，而不是悄悄回退到默认值：

    _BUILDERS = {"v1": build_v1, "v2": build_v2, ..., "v2_0818": build_v2_0818}

def build(version, enabled_tool_names, *, enabled_corpora=(), business_names=()):
    try:
        builder = _BUILDERS[version]
    except KeyError:
        raise ValueError(f"unsupported version {version!r}; supported: {sorted(_BUILDERS)}")

    难点在参数演进：新版本需要新参数，老版本签名里没有。解法是用签名探测决定传不传，老版本一行都不用改：

    params = inspect.signature(builder).parameters
if "destinations" in params:
    kwargs["destinations"] = tuple(destinations)
if "queues" in params:
    kwargs["queues"] = tuple(queues)
return builder(normalized_tool_names, **kwargs)

    七个版本共存的代价是仓库里躺着约 2100 行 prompt 代码。为什么不清掉旧版本？因为回滚要能用：现场出问题时，改一行配置就能退回上一版，而不是 revert 一次提交再重新发版。

    版本文件数行数说明
    v14260初版
    v25299第一轮结构重排
    v2_081252998 月 12 日版
    v2_081353248 月 13 日版，次日又改
    v35158精简版，最短的一版
    v45299拆成 identity / behavior / 两类工具用法
    business_v2_08186536最长的一版，当前启用

    版本名里带日期（v2_0812、v2_0813）不是随意起的：它记录了一天一版的迭代节奏。两个相邻版本只差一天，说明那两天在拿真实对话反复试。

    两套相反的版本策略

    同一个仓里还有另一套 prompt，策略完全相反：

    对话 prompt压缩 prompt
    版本数7 个，可配置切换1 个实现，版本号写死
    切换方式改配置即可写死 v3，其他值直接抛异常
    为什么话术和策略本来就要反复迭代输出是格式契约，下游要解析
     
    def __post_init__(self) -> None:
    if self.prompt_version != "v3":
        raise ValueError("context compression prompt version must be 'v3'")

    压缩 prompt 的输出要被程序解析成结构化的摘要和事实，一旦文本格式漂了，解析就崩——所以它宁可拒绝启动，也不接受第二个版本。这是同一个团队对两类 prompt 给出的两个相反答案，判断依据是：漂了谁会疼。人读的 prompt 可以漂，机器读的不行。

    改完怎么知道没变差

    prompt 改动最难的部分不是写，是证明它变好了。靠"聊两句感觉还行"是不成立的，因为模型的行为是分布的，你看到的永远是个位数样本。

    做法是建一套离线评测，用固定的 case 集跑：

    指标回答什么问题
    工具路由准确率该调工具的时候调了吗？调的是对的那个吗？
    参数差异调对了工具，但参数填错了——这类错误比调错工具更隐蔽
    异常 turn 全量输出不只看平均值，把每一个坏掉的 case 原文打出来
    真实日志离线重放拿线上真实对话重跑，比造 case 更接近真相
    工具耗时聚合prompt 改动会让模型多绕几步，耗时是最早暴露的信号
    多模型对比同一版 prompt 在不同模型上的表现，决定该换 prompt 还是换模型
    ⚠️

    只看总体准确率会骗人

    两个版本可能总体准确率一样，但错的 case 完全换了一批。所以比"准确率涨了几个点"更有用的，是逐条对比"哪些 case 变了、从对变错的是哪几类"。改 prompt 最典型的失败是把一类问题修好、顺手弄坏另一类，而平均值刚好抵消。

    这套评测的价值不在于给出一个分数，而在于让 prompt 改动从"信仰"变成"证据"。有了它，才敢在一天里连改两版。
