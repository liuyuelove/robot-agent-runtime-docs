    复盘与取舍 14

    这套东西不是设计出来的，是改出来的——而且第一版被整体放弃了。先说它从哪来，再说哪些判断站住了、哪些是过度设计、哪两个坑教得最多。

    它从哪来：一次重写，不是重构

    在现在这套代码之前，有一代跑得起来的原型。它的形状很典型：仓库根目录平铺着 8 个 Python 脚本和 5 个 *.html 页面，src/ 里是 LangGraph 的 nodes/、subgraphs/、graph_builder.py 直接堆在一起，设备调用散落在各个 node 内部，工具则是一批一次性脚本。

    它跑通了全链路，也真的被用过。但到了要接第 5 个设备、第 3 类业务的时候，改一处要动十几个文件，而且没人能说清"这段逻辑该归谁"。

    维度第一代原型现在这套
    仓库根目录16 个脚本与页面平铺只剩 pyproject.toml 和启动脚本
    src/ 形状nodes / subgraphs / graph_builder 平铺九层，依赖方向单向
    设备接入在 node 里直接调 SDK / HTTP27 个 Public Adapter，Runtime 统一管生命周期
    模型能力工具是散落脚本，Schema 手写18 个注册 Tool，Schema 与入口自动推导
    配置单个 config.py三级合并 + 启动期类型化，运行期不可变
    测试61 个文件，无架构约束151 个文件，其中 21 条是架构守护

    为什么是重写而不是原地重构，三个理由：

    1. 坏的不是代码，是共识。原型里没有"谁负责什么"的成文约定，所谓重构就是边改边吵。先把准则写下来，再按准则写代码，反而更快。
    2. 边界已经渗进细节。设备调用散在 node 里，意味着"把它抽出来"必须同时改业务逻辑——改动面大到没法评审。
    3. 旧系统不能停。机器人还在现场跑，所以新仓并行开发，跑通再切。

    代价是真实的：两套代码并行了一周左右，能搬的只有 prompt 文本、知识库和业务话术，代码基本重写。总代码量大约翻了一倍——多出来的部分主要是测试，以及每个 Adapter 都要付的固定样板环——配置、事件、快照、组装、两份文档，再加一套合同测试。

    ⚠️

    什么时候该重写

    判断标准不是"代码烂不烂"，而是"共识能不能先写下来"。如果团队能就分层职责和依赖方向达成一致，重写就只是工程量；如果达不成，重写只是把混乱换个地方放。

    做对的

    决策当时的理由事后验证
    Adapter 三分类 + Real/Mock 合同一致 设备太多、换型太频繁 后期新增设备基本只写一个目录，上层零改动
    Tool 代码注册、Schema 自动推导 手写 Schema 已经漂移过 这类 bug 彻底消失
    事件只表事实 避免总线变成隐式 RPC 因果关系可读，排查时能顺着事实链走
    架构守护测试 AI 和人都会顺手越界 规则从"评审意见"变成"提交就红"
    配置启动期一次成型 边缘设备不接受半启动状态 消掉一整类配置竞态

    代价与过度设计

    做法问题后来的处理
    几乎所有进程内组件都包装成 Engine 十行的格式化函数也配 Factory + Config + 注册 + 测试 补了六项准入门槛，明确"不满足就别包装"
    早期准则文档互相重叠 三份文档都说自己算数，AI 随机选一份 合并为唯一准则目录，旧文档降级为背景
    事件总线一度被期待提供可靠投递 讨论了很久要不要做重试和顺序保证 明确写进"不承诺"清单，谁依赖谁自己保证
    重写的决定拖到"改不动"才下 在原型上多付了两个月的利息，每天修的是结构性问题 没有补救，只能事后承认这一步该更早

    两个案例

    下面两个都不是架构层面的决策，是具体踩到的坑。挑它们是因为：教训能迁移，而且都不是"下次小心一点"能解决的。

    案例一："导航完成"不等于"到达"

    现象。机器人在 IDLING_STATIONARY 和 RESETTING_MOVING 之间来回切换，肉眼可见地抖，隔几秒一次，停不下来。

    定位。日志里是一条闭环：回位导航完成 → 收口到驻停 → reaction 认为"该回迎宾点" → 又提交一次回位导航 → 完成 → 收口……每一环单独看都是对的。

    根因。判定"我在迎宾点上"用的是导航 operation 完成这个事件。但 operation 完成只说明这次导航结束了，不说明机器人确实站在那个点上、朝向也对。定位误差让"已经到了"和"还该去"同时成立，环就闭合了。

    修法。把"到点"从事件改成状态判定：同时校验位置距离和朝向角，两个都满足才算"已在点上"，此时跳过导航直接收口。事件只负责触发判定，不再直接当结论。

    💡

    可迁移的一条

    凡是"外部系统告诉我做完了"的地方，都要再问一句：它做完的是动作，还是我真正想要的结果？动作完成是事实，结果达成是判定，两者之间隔着一次校验。

    案例二：与逻辑、或逻辑，改了两遍

    现象。"机器人该不该回到空闲"这个判断依赖两个传感器：人体在场、人脸在场。第一版用与——两个都在才算有人。结果人脸漏检时机器人永远不返回，站在那儿对着空气等人。

    于是改成或——任一个在就算有人。这回反过来了：路过的人影、屏幕反光、半张侧脸都会触发返回，对话被频繁中断。

    最后改回与，但不是简单地改回去。真正的问题不在运算符，而在把两个都不可靠的传感器当成了可靠输入。补的是判定层：人脸要连续 10 帧稳定才算"在"，离开要连续丢帧再加 3 秒确认才算"走"。

    🧭

    可迁移的一条

    当一个二值判断反复改都不对，通常不是逻辑运算符的问题，而是输入本身带噪声。这时候该加的是去抖和确认窗口，不是换一个运算符再试一次。

    如果重来

    • 准则目录第一天就建，而不是等文档打架了再合并——返工成本远高于初始成本；
    • Engine 门槛提前定，否则会先造一堆再删，删的时候还要动测试和文档；
    • 暂停矩阵这类多源竞争逻辑，先画表再写码——这一块返工最多，因为它无法靠读代码理解，只能靠表格穷举；
    • 重写的决定要更早下——等到"改一个设备要动十几个文件"才动手，前面那些天其实都在为结构性问题付利息。

    可迁移的经验

    🎯
    先定义"不许做什么"
    每层的价值来自它的禁止项，而不是它的职责描述。职责会膨胀，禁止项不会。
    🔒
    把不确定性关进少数几个地方
    模型不确定、设备不确定、人也不确定。不要试图消除，而是收敛到可枚举的状态协调器里。
    🧪
    能自动检查的规则才叫规则
    写在文档里的是建议，写成断言的是约束。前者约束愿意读的人，后者约束所有人。
    ⚖️
    承认取舍的场景性
    "不支持热更新"在云上不可接受，在机器人上很合理。写结论时要带上前提。
