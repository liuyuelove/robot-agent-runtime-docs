    可观测性 12

    这类系统的 bug 大多不是崩溃，而是"行为不对"。没有栈可看，只能靠日志重建因果。所以日志在这里不是调试附属品，是主要证据链。

    单行 JSON，固定 schema

    每个进程写自己的时间戳文件，超过阈值滚动分片：

    logs/20260101-120000-123.jsonl
logs/20260101-120000-123.jsonl.000001

    每条记录都带：

    字段作用
    ts固定时区 ISO 时间戳
    event点分命名的事件名，如 agent.model.request.prepared
    process_instance_id区分同机多次启动
    session_id / run_id / trace_id跨文件、跨分片聚合同一轮交互

    按 Run 分解耗时

    一个分析脚本可以把一次 Run 拆成阶段耗时：

    会话加载 → pre-graph → Graph → 模型推理 → 工具执行 → 输出 → 状态提交

    再加上里程碑（tool call 生成、tool result 可用、最终回答生成）相对循环起点的时间。这套东西让"这轮为什么慢"从猜测变成读数：是模型首包慢、是某个工具卡住、还是持久化拖尾。

    💡

    跨进程聚合

    同一个 run_id 可能横跨多个进程文件和多个滚动分片，分析脚本会合并后再算，不会因为重启把一次 Run 切成两半。

    内容开关 ≠ 脱敏

    🚫

    关掉正文采集不等于脱敏

    关掉 include_content 只是不记对话正文；日志里仍然有用户标识、业务元数据、错误分类和栈帧位置。生产环境必须配合目录访问控制、保留期和审计策略。

    这条写进文档是为了防止一种很常见的误判：以为"我把正文关了所以日志可以随便传"。日志本身就是敏感资产。

    磁盘水位

    边缘设备磁盘小，日志写满会把整机搞死。所以有一组水位阈值：正常 → 高位（减少正文采集）→ 严重 → 耗尽（只记骨架）。恢复时带滞回，避免在阈值附近反复抖动。

    设计上还有一条：日志系统的任何失败都不许改变业务语义。写日志失败不能让一次对话失败。
