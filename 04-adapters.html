    Adapter 体系 04

    27 个外部边界，每个都要能被替换、被 Mock、被单独测试。这一章讲的是：怎么判断一个东西该不该是 Adapter，以及一旦是了，它必须满足什么。

    三类判定

    分类判断标准典型对象必须 Real + Mock
    Hardware连接物理设备或厂商硬件 SDK底盘、业务屏、自助设备、环形麦、门禁✅
    Integration连接进程外软件服务或第三方平台语音识别 / 合成、数字人、地图、检索、行情、充电桩✅
    Engine只在当前进程内运行的技术状态机或聚合器输入总线、输出总线、机器人状态、人体存在判定不强制

    分类不是按目录分的，是按失败模式分的。Hardware 和 Integration 会连不上、会超时、会返回脏数据，所以必须有 Mock 才能写测试；Engine 的失败是逻辑错误，用假实现反而掩盖问题。

    Real / Mock 的合同一致

    硬性要求：同一个 Adapter 的 real.py 和 mock.py 必须导出同一组类型——相同的 Event、相同的 Snapshot、相同的错误分类。测试里用 Mock 跑通的链路，换 Real 不能因为"事件字段不一样"而崩。

    这条规则的价值在联调阶段最明显：Mock 不是"随便返回点东西的桩"，它是对真实设备行为的一份可执行假设。当 Mock 和 Real 行为不一致时，说明我们对设备的理解错了——这个错误在测试里暴露，比在现场暴露便宜得多。

    💡

    纯进程内组件不必强行对称

    Engine 不为了"目录好看"去造空的 Real/Mock。只有当它真的需要两种实现时才分。这条后来救回了不少无谓的样板代码。

    从 0 到 1 写一个 Adapter

    前面几节讲的是规则，这一节讲怎么落地。样本是一个真实存在的 Integration Adapter（数字人显示），最终形态是 15 个 Python 文件（含 transport）、2 份文档、4 个测试文件。下面按动手顺序走，每一步说清楚：先写什么、为什么先写它、容易踩什么坑。

    第 0 步：先判断该不该做成 Adapter

    写代码之前先回答三个问题：

    1. 有没有外部系统？网络、进程、设备、SDK——任何一个都算。
    2. 有没有生命周期？要不要 start() / stop()、会不会断线重连、退出时要不要清理资源。
    3. 有没有第二个调用方？只有一个地方用的话，包一层只是多一次跳转。

    三个都是"是"，做成 Adapter；只有一个"是"，写普通类。这一步判断错了，后面九步全是白做。

    第 1 步：先定合同（__init__.py，19 行）

    第一件事不是写实现，是决定对外暴露哪些符号。这个文件只有 19 行，却是整个模块唯一的门：

    from .adapter import DigitalHumanAdapter
from .config import DigitalHumanConfig
from .events import DigitalHumanConnectedEvent, DigitalHumanFrameReceivedEvent
from .models import DigitalHumanSnapshot
from .factory import create_digital_human_adapter

__all__ = ["DigitalHumanAdapter", "DigitalHumanConfig", ...]

    四类符号：Adapter（能调什么）、Config（怎么配）、Event（发生了什么事）、Snapshot（现在什么状态），外加一个 factory。

    坑：不要导出 RealXxxAdapter / MockXxxAdapter、transport、内部异常类型。一旦导出，别人就会写 isinstance 判断，Mock 从此换不掉。

    第 2 步：Snapshot——外部能查到什么（22 行）

    Snapshot 是"这个模块现在怎么样"的唯一答案，也是排查问题的入口。放进去的字段要满足两条：稳定（不随实现变化）、可观测（外部真的会看）。

    典型内容：是否已启动、是否已连接、消息与事件计数、最后一次错误、最后一条事实的关键值。

    坑：不要放 use_mock、实现类名、原始 payload。Snapshot 里一旦有这些，等于把实现细节升格成合同。

    第 3 步：Event——它发生了什么（30 行）

    只发已经发生的事实，不发命令、不带请求意图。命名固定为 <模块><事实>Event，字段递归不可变。

    一个 Adapter 通常只发三五个事件：连接建立、连接断开、业务事实、失败。业务事实要归一化——把供应商的 payload 翻译成自己的语义，而不是把 payload 塞进事件里。

    坑：事件里带原始 payload，等于让下游依赖供应商格式。以后换供应商，下游全要改。

    第 4 步：Config——需要哪些参数（75 行）

    一个类型化 dataclass 加一个 parser。parser 从合并后的配置字典里取值、校验、给默认值；构造一次，之后不可变。

    这个 Adapter 的配置项大致是：device_id、use_mock、endpoint、连接超时、接收超时、重连间隔、心跳参数。

    坑：模块内部不要直接读 YAML 或环境变量。配置只能从构造器进来，否则测试里换不掉。

    第 5 步：共享核心（runtime.py，423 行）

    这是最重的一步，也是决定成败的一步。runtime.py 承担三件事：

    1. 状态机：未启动 / 连接中 / 已连接 / 重连中。所有对外状态都从这里推导。
    2. 串行化：同一时刻只处理一条消息，避免并发回调把状态改乱。
    3. 翻译：把 transport 递上来的原始消息，经协议层解码，变成公共 Event。
    💡

    为什么 Real 和 Mock 共用这一层

    因为"合同一致"如果是靠纪律保证的——"写 Mock 的时候记得跟 Real 对齐"——它迟早会漂。把两者共同的部分放进 runtime、只让 transport 分叉，"一致"就变成了结构上的必然：它们跑的是同一份代码。

    第 6 步：transport——真实的与假的（385 / 88 行）

    transport 只做两件事：把字节搬进来搬出去，以及管理连接本身（建连、断线、重连、背压）。它不认识业务、不发事件、不做判断。

    Real 那 385 行基本都花在连接管理上：重连退避、心跳、半包拼接、异常分类。Mock 那 88 行模拟同样的接口——走同一套方法签名，不是 if 分支。

    第 7 步：real.py / mock.py 为什么只有 18 行

    因为走到这里已经没有可写的了：共享核心在 runtime，差异在 transport，这两个文件只负责把对应的 transport 塞进 runtime。

    def create_real(config):
    return DigitalHumanRuntime(transport=WebSocketRealTransport(config.transport))

def create_mock(config):
    return DigitalHumanRuntime(transport=WebSocketMockTransport(config.transport))

    18 行不是偷懒，是前五步把该分的地方分干净的结果。如果这两个文件涨到 300 行，说明业务逻辑漏进了实现层。

    第 8 步：测试从哪开始（1679 行）

    顺序建议：协议解码 → runtime 状态机 → transport 重连。由内向外，每层都能独立测。

    测试文件行数测什么
    test_protocol.py179帧解析、序号、心跳、畸形输入
    test_runtime.py1116状态迁移、串行化、事件归一化、失败分类
    test_transport.py242建连、断线、重连、半包
    test_config.py142默认值、校验、非法组合

    test_runtime 最长，因为它要覆盖"连接态 × 消息类型 × 失败原因"的组合——正是最容易出 bug 的地方。默认测试不连真实设备，这就是 Mock 存在的意义。

    第 9 步：接进系统（factory + composition root + 文档）

    最后三件事：

    1. factory：根据 Config 决定造 Real 还是 Mock，返回公共 Adapter 类型。
    2. composition root：启动时注册模块、传入 Config。禁用时不构造，运行期不懒加载。
    3. 两份文档：README 写机制（职责、公共入口、事件、快照、边界），AGENTS 写给 AI 的规则（能改什么、不能改什么）。

    坑：不要在 import 时创建实例。模块被 import 不代表它该启动。

    检查项不合格的表现
    三个问题都是"是"只有一个调用方却包了一层 Adapter
    __init__.py 没有导出 Real / Mock 类外部写了 isinstance 判断
    Snapshot 里没有 use_mock / 类名 / 原始 payload测试断言依赖实现细节
    Event 只有事实，没有命令出现 RequestXxxEvent 这类名字
    模块内没有直接读 YAML / env测试里没法改配置
    Real 和 Mock 跑同一份 runtime两份实现各写一遍状态机
    transport 里没有业务判断transport 里出现 if 业务字段 ==
    real.py + mock.py 不到 50 行涨到几百行，说明逻辑漏进实现层
    默认测试不碰真实设备CI 需要连内网才能跑
    import 时不创建实例跑一次单元测试就发起了网络连接

    生命周期与 facade

    所有 Adapter 实例由唯一的 AdapterRuntime 管理，顺序固定：

    factory 创建（未启动）
  → 组装 AdapterSet
  → 绑定公共 facade
  → 按稳定顺序逐个 start()
  → 任一失败：反向清理已进入启动流程的实例 + 解绑 facade
  → 全部成功：开放外部入口

关闭时严格反向：先停入口与消费者，再停 Adapter，最后解绑。

    调用方只通过一个入口拿实例：

    from src.adapters import adapters   # 允许在模块顶层 import

def execute(self, tool_input):
    nav = adapters.navigation      # 只在受控时机解析实例
    return nav.navigate_to(target)

    注意这两行的区别：import facade 可以，解析实例不行。因为 import 时 Runtime 可能还没绑定，拿到的是空的。

    为什么禁止构造器注入

    构造器注入会让"依赖"变成对象的构造前提，于是一串连锁反应：测试要先造 Adapter、启动顺序要人工维护、模块之间开始互相 import 具体类。改成运行期取，所有这些都消失了，代价是"拿到可能为空"——而这个代价被 facade 明确表达为一种可处理的错误。

    Engine 的六项准入门槛

    "在进程内运行"是 Engine 的必要条件，不是充分条件。想升级成 Engine Adapter，必须满足六项中的至少三项：

    #条件反例（不满足就别包装）
    1进程级共享实例每次调用 new 一个的转换器
    2有需要统一管理的生命周期或资源纯函数
    3两个以上独立调用方只被一个模块用的策略类
    4需要可替换的稳定公共合同内部实现细节
    5发布公共 Event 或提供公共 Snapshot只返回布尔值
    6内部状态跨多次调用持续存在无状态 helper

    这个门槛是事后加的。早期版本里几乎所有进程内组件都被包装成了 Engine，结果是为一个十行的格式化函数配了 Factory、Config、Runtime 注册、facade 字段和一整套测试。门槛的作用不是提高标准，而是给"不要包装"一个可以引用的依据——否则每次评审都要重新吵一遍。

    ⚠️

    业务状态机不是 Engine

    业务状态机属于 domain，不许因为"它在进程内"就塞进 Engine。判断依据是：它管的是业务规则还是技术资源。
