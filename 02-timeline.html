    端到端时序 02

    上一章给的是边界，这一章给的是时间。同样一条链路，换成按「谁在什么时候产生了什么事实」读一遍——包括那些不翻代码根本想不到的绕路。

    九跳：一次对话穿过哪些环节

    先给位置，再给时间。下面这张表是纵向的：从声波进来到声音出去，一共九跳。

    #从 → 到经手的东西谁能在这里拦下它
    1声波 → 识别文本环形麦 → ASR transport唤醒词、VAD 端点判定
    2识别文本 → 输入事实SpeechInputBridge → Brain Input活跃会话匹配、空文本丢弃
    3输入事实 → 状态感知事实RobotState 转发矩阵转发矩阵——这一跳最容易被读漏
    4状态感知事实 → 一次 runInput Ingress → Run Coordinator抢占规则、排队顺序
    5run → 模型增量Agent（LangGraph）上下文预算、工具调用上限
    6增量 → 输出事实Brain Output合同校验、sequence 生命周期
    7输出事实 → 字幕UI Display Bridge → SSE前端连接状态
    8输出事实 → 声音Speech Output Coordinator → Streaming TTS切段阈值
    9播报状态 → 数字人Digital Human Adapter运动状态防抖

    注意第 3 跳：输入不是直接进模型的。它要先去状态机那儿领一次「现在允许被听见」的许可。这一跳没有任何日志会告诉你「被拦了」，因为「没听见」本身就是设计。

    时间轴：T0 到 T12

    把上面九跳摊在时间上，就是下面这张表。最后一列是「站在用户面前能看到什么」——排查问题时，这一列往往比日志更快定位到断在哪一跳。

    时刻发生了什么产生的公共事实用户能感知到什么
    T0 人走近，或说出唤醒词；环形麦给出声源方位，人体感应给出「有人」 运动感知类事实（方位 / 在场 / 人脸候选） 还没有反应
    T1 状态机判断「这个事实在当前状态下要不要听」 放行则产出 RobotStateAware*；不放行则到此为止 仍然没有反应
    T2 会话激活或切换：新建会话、清空上一轮的聊天显示 会话激活回调（ASR 与数字人同时被通知） 屏幕亮起、数字人抬头、聊天记录清空
    T3 ASR 绑定到当前会话，开始收音 SpeechInputPartialRecognizedEvent 屏幕上出现实时字幕，边说边出
    T4 VAD 判定说完，ASR 给出最终结果 SpeechInputFinalRecognizedEvent 字幕定格，不再变化
    T5 输入被本地接受：校验、去重、补 session_id BrainInputReceivedEvent 上一轮播报立刻停，并响一声提示音
    T6 这条输入再过一次转发矩阵，拿到「可以进推理」的许可 RobotStateAwareBrainInputReceivedEvent 无
    T7 装配上下文，模型开始输出 BrainOutputLlmStreamStartedEvent 数字人开始有动作（口型待命）
    T8 第一段增量文本到达 BrainOutputLlmStreamChunkAppendedEvent 字幕逐字出现；同时开始说话
    T9 模型决定调用工具 BrainOutputToolCallRequestedEvent 屏幕上出现工具卡片；可能需要一句「稍等」
    T10 工具返回，模型带着结果继续输出 BrainOutputToolCallResultPublishedEvent + 新 chunk 继续说，内容里带上了工具的结果
    T11 本轮输出结束 BrainOutputLlmStreamCompletedEvent 说完；字幕保留在屏幕上
    T12 会话进入等待，看门狗开始计时 无（计时器不是事实） 无——但这一段时间决定会话什么时候结束
    ⚠️

    T5 和 T6 是同一件事的两次事实

    一次是「输入被本地接受」，一次是「输入被状态机放行」。中间夹着转发矩阵——所以「用户说了话」和「模型听见了话」不是同一时刻。把这两件事合成一件，后面所有关于「为什么它没反应」的排查都会失焦。

    为什么输入要绕状态机一圈

    因为 Brain Input 只做三件事：校验、去重、补 session_id。它不判断「现在该不该听」。判断权在状态机的转发矩阵里。

    后果很直接：换个状态，同一句话的命运就完全不同。

    当前状态用户说「带我去三号柜台」结果
    IDLING_STATIONARY放行正常进入推理
    BUSINESS_STATIONARY放行正常进入推理
    IDLING_MOVING拦下模型完全不知道有这句话
    WELCOMING_MOVING放行正常进入推理——移动迎宾要边走边听

    这张表的第三行是这套设计最容易被误判成 bug 的地方：机器人在走，用户在说话，它没理人。这不是漏了，是它在移动时不应该被路边的一句话带走。第四行则是反过来——移动迎宾恰恰需要听见。

    装配、预算、推理

    进入推理之前，要先装配一份工作状态，通常包含四样东西：

    • 历史消息——被压缩过的前文，不是原始全量；
    • 业务上下文——当前正在办的事，以及办到哪一步；
    • 已确认事实——「办过」和「办成了」分开存的那两类；
    • 当前机器人状态——它现在能做什么，不能做什么。

    压缩检查发生在装配时，不是推理时。这是个有意的位置选择：等到模型报「上下文超了」再压，这一轮已经废了；在装配时按预算压，最坏情况只是这一轮的历史短一点。

    提示词也在这个阶段拼装——按当前启用的工具渲染。所以模型看不见一个没启用的工具，也就不会去调它。

    推理本身是标准的循环：模型 → 工具 → 模型。这里只有两条容易忽略的约束：

    约束一：部分工具在同一轮 run 里只允许调用一次，用来阻断「同一个工具反复扇出」和重复副作用。

    约束二：模型返回空流时只重试一次。重试是兜底，不是常态——反复重试只会让用户等得更久。

    工具期间不许静音

    工具可能是一次导航、一次检索、一次取号，几秒钟起步。这几秒钟如果什么都不说，用户会认为「它卡住了」。

    所以有一条可配置的规则：某个工具开始时，播一句固定话术，每轮 run 只播一次。这句话不是模型生成的，它走的是 Brain Output 的另一个入口——固定话术通道，不经过推理。

    于是这一刻字幕和语音会分叉：

    字幕语音
    T9 工具开始出现工具调用卡片（叫什么、参数是什么）「稍等一下」
    T10 工具返回卡片变成完成态模型生成的正式回答

    这不是「界面和语音不同步」，是两条通道各自干自己该干的事：界面要让人看见它在做什么，语音要让人知道它还在。

    一路输入，两路输出

    Brain Output 之后，同一个 chunk 事实被两个订阅者各取一份，走两条完全不同的路：

    字幕路声音路
    处理粒度每个 chunk 立刻投影先进缓冲，攒够再切段
    起播条件无条件达到最小字符数，或遇到指定标点
    为什么这样字幕慢一个字，用户就会觉得卡一个词一个词地合成，语气会碎
    被打断时保留已显示内容立刻停止，且不再播剩下的缓冲

    所以「先看到字、后听到声」是设计结果，不是延迟。反过来，如果字幕比声音慢，那才是问题。

    三条打断路径

    打断不是一种机制，是三种，触发源完全不同。

    触发谁发起对正在播的声音对正在跑的 run
    用户说完一句，输入被接受 Speech Output Coordinator 立刻打断，并播一声提示音 不动
    新一轮输入到达，而上一轮还没收尾 Run Coordinator 打断 旧 run 标记为「已被取代」并取消，新的立刻开始
    run 失败或被取消 Run Coordinator 打断 结束，不再产生输出

    第二种有个例外要单独说：如果上一轮已经在收尾，新输入不抢占，而是排进待执行队列；控制类输入（不是聊天，而是「停一下」「回迎宾点」这类）永远排在最前面。

    🧭

    这条规则真正的含义

    用户说新话的代价，是上一轮被丢弃，而不是「排队等它说完」。在服务场景里，人改主意比机器把话说完更重要——所以宁可扔掉半句话，也不让人等。

    哪些延迟能测，哪些测不到

    这条链上有五个可观测的锚点，覆盖了从「说完」到「听见」的大部分区间。但它们各自只说明一件事，混用会得出错误结论。

    锚点覆盖区间它到底说明了什么
    VAD 起止时间用户说话的时长VAD 检测到的边界，不是真实声学首音节
    ASR 结果时间说完 → 出字识别本身花了多久
    ASR 首字延时说话中 → 第一个字由 provider 上报，不是所有 provider 都给
    首段内容进入 TTS模型首段 → 进入播报链路应用层已经把它交出去了
    首段提交成功交给 TTS 服务成功只表示请求发出去了，不表示已经开口
    播报开始真的开始出声这才是用户能听见的起点
    ⚠️

    最容易搞错的一个指标

    「首段提交成功」经常被当成「用户已经听到」。它其实只证明 transport 调用返回了。用它算端到端延迟，会系统性地少算一段——而这一段恰恰是 TTS 服务最不稳定的一段。

    每一跳挂了会怎样

    这张表是整章最实用的一页：出问题时，先用「用户感知」那一列定位，再去对应的锚点看日志。

    断在哪表现兜底用户感受
    ASR 断线没有字幕，也没有输入transport 重连；会话不受影响「它没反应」
    转发矩阵不放行说话没反应这是设计，不是故障同上——但换个状态就好了
    模型超时 / 空流没有输出重试一次，仍失败则发失败事实沉默，或一句兜底话术
    TTS 不可用有字幕，没声音字幕路继续能读，不能听
    数字人不可用有声音，没口型语音路继续能听，不好看
    前端连接断字幕停在某处语音继续；重连后取快照声音正常，字不动

    这张表的每一行都指向同一个判断：没有任何一跳的失败会让整条链停摆。这不是巧合，是优先级排出来的结果——在服务现场，「还能说话」比「正确」重要，「有字幕没声音」比「整机黑屏」好。

    要按这条链查日志，锚点和查询顺序见 12 可观测性；状态机为什么放行或拦下，见 08 的转发矩阵。
